# v3 — build order

Two design documents now describe one release.
[`agents.md`](agents.md) makes the platform agent-agnostic;
[`scoping.md`](scoping.md) reorganises who can see and change what. Their
tasks interleave, and several share a file. This document is the order, the
dependencies, and what is blocked. It adds no design — where it is thin, the
source document is normative.

## 1. What v3 is

Three changes, in the order they matter to a customer:

1. **An admin can hand out capability deliberately.** Nothing is shared by
   containment; an org builds once and scopes to named units
   ([`scoping.md`](scoping.md) §0).
2. **Administration inherits.** Boundary already flows down; connectors,
   people and audit must too ([`scoping.md`](scoping.md) §5.5). This is the
   difference between a tree that governs and a tree that only draws.
3. **The agent is a choice, not an assumption.** `harness run pi` and
   `harness run claude` over one unchanged set of assets
   ([`agents.md`](agents.md) §0). Largely built — 14.2, 14.3 and 14.5 are
   done.

## 3. Shared files — the collision map

Two tasks in the same wave must not touch the same file. This is the reason
for the wave boundaries, not task size.

| File | Tasks | Resolution |
| --- | --- | --- |
| `backend/app/domain/org_tree.py` | S5, A6 | S7 turned out not to need it. S5 and A6 must still not run concurrently |
| `backend/app/domain/resolve.py` | S1, S6 | different waves |
| `backend/app/api/routes_assets.py` | S1, S2, S6 | different waves |
| `pi/packages/harness-cli/src/adapters/*` | A6, A1 | different waves |
| `web/app/admin.tsx` | S3, S4, A9, A10 | all wave 4, all blocked (§4) — and they must run **one at a time** |

## 4. What is blocked, and why

**Every console task.** `web/app/` has around eighteen uncommitted files —
`admin.tsx`, `ui.tsx`, `globals.css`, plus new `login/`, `auth.tsx`,
`home.tsx`, `hero-*.tsx`, `theme-picker.tsx` and others. Four wave-4 tasks all
edit `admin.tsx`. A delegated agent cannot tell in-flight work from a
regression, and neither can a diff.

Wave 4 starts when that tree is committed. Nothing else waits on it.

## 5. The one irreversible step

S1 backfills `asset_scopes` for every existing asset
([`scoping.md`](scoping.md) §4.1). Get it wrong and every live session
resolves an empty manifest on deploy.

It is reviewed before it is applied, and its acceptance test is not "the
backfill ran" but **"every pre-existing manifest is byte-identical after it"**.
That is the only check that distinguishes a correct backfill from a plausible
one — and it is still not sufficient on its own: byte-identical holds over the
tree *as it stands at migration time*, and says nothing about the units added
the following week. Both tests exist ([`scoping.md`](scoping.md) §4.1).
